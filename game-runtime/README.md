# Muguet OHOS game runtime

This is a source port of Muguet commit `1a0300d3cfc5f87ce2fa1ccb365c013e5238e322`, licensed under GPL-3.0-or-later. It executes the supplied game's real memory64 WebAssembly through Wasmtime 49.0.0, with the upstream native filesystem, HTTPFS data reads, shared-memory worker threads, input block, renderer command ring, and native Opus hooks.

`src/lib.rs` replaces the Apple executable entry point with an OHOS static library. `src/ffi.rs` starts the guest on a background thread. The ArkTS/XComponent application supplies a retained NativeWindow and application files directory. The resource layout is `<files_dir>/game/data` and `<files_dir>/game/b/<build>/shaders`; saves are kept separately in `<files_dir>/saves`.

The Emscripten main-thread JS proxy is implemented from the supplied archive's exact 38-entry function table. It preserves tagged memory64 arguments, dispatches native filesystem/pthread operations, and completes asynchronous Wasm contexts through `_emscripten_run_js_on_main_thread_done`. Its argument decoder has two focused Rust tests in `logs/proxy-decode-tests.log`. Socket bind/listen explicitly return the same ENOSYS result as the offline runtime's other socket operations.

The host AOT tool applies upstream patch version 11 and fails if any of its nine required named hook targets, the TLS global, or native malloc are absent. All nine hooks are present in this package's real Wasm input. `logs/game-wasm-metadata.json` records the patched module's imports, memories and exports. Its imported shared memory64 begins at 3 GiB and declares a 16 GiB maximum. The mobile runtime caps growth at 5 GiB; the AOT compiler uses the same 5 GiB reservation and 64 KiB guard configuration.

The complete trusted AOT ELF is embedded into the application's signed executable mapping through `artifacts/game-embedded.o` (symbols `mg_game_aot_start` and `mg_game_aot_end`). Runtime uses `Module::deserialize_raw` with a no-op code publication callback only for these already executable signed bytes. It does not compile or grant execute permission to sandbox files.

Build with the official Rust 1.99.1 `aarch64-unknown-linux-ohos` target and the HarmonyOS SDK:

```sh
bash game-runtime/scripts/compile-aot.sh /absolute/path/game.wasm
bash game-runtime/scripts/build-ohos.sh
bash game-runtime/scripts/embed-game.sh
```

Link `artifacts/libmuguet_game_runtime.a`, `artifacts/game-embedded.o`, and `native-platform/src/oh_audio.cpp` into the HAP's native shared library. The Vulkan OHOS surface patch is in `vendor/wgpu-hal`; `vendor/wgpu-core` preserves upstream renderer fixes. OHAudio consumes the real 48 kHz stereo F32 guest ring. The public C ABI is in `include/muguet_game_runtime.h`.

The guest initially renders at 0.4 of the physical dimensions with even dimensions and the upstream mobile minimum aspect ratio, targeting 30 FPS. Resize and touch coordinates use the same guest dimensions. Native rendering is measured by `presents`; guest render requests are counted separately by `guestPresents`. Neither counter on its own establishes a playable scene. Runtime stages, errors, host calls, input count and memory statistics are available as JSON; full native/guest logs go to `<files_dir>/game-runtime.log`.

Lifecycle currently supports one game runtime per application process, as upstream shared globals and workers use process lifetime. Stop requests suspend presentation/audio, release focus and make subsequent imported host calls trap. Restart the application process to start another game runtime. Apple controller polling is replaced by C ABI key/button/control injection. Public OHOS thread QoS targets the GPU, game main and named render threads, with Set/Get outcomes recorded at startup; it does not force CPU/GPU clocks. Apple-only allocator/compression/GPU statistics remain unimplemented. The optional multiplayer meme sound helper still searches for a desktop `afplay` executable if custom sound assets exist; core game audio uses OHAudio.

`config.json` in the app files directory enables `depth_reduce_opt`, `depth_reduce_no_zero` and `thread_qos` by default, including when those fields are absent from an existing file. Explicit boolean `false` disables each setting for A/B; strings, numbers and null are rejected as off. Restart the process after changing pipeline or QoS settings. The depth optimization requires the exact supplied shader SHA, pipeline label and six immutable constants. Only that verified shader can disable automatic workgroup zero initialization; it writes all 1536 shared words before the first shared read. Other shaders keep the default initialization and existing bounds guards.

`cpu_profile`, `gpu_profile`, `gpu_diagnostics` and `sync_submit` default to false. Existing explicit values are respected; set them to false for ordinary play. An explicit `"resolution":"1202x800"` with `"fps_limit":30` fixes the qualified target dimensions; the unchanged default scale of 0.4 otherwise follows the physical surface. Updates preserve the app files, game assets and saves. The optional `vulkan-buffer-probe-request.json` diagnostic marker must be absent for normal game startup.

Cross compilation and linking do not establish device rendering or gameplay. Record device observations separately.

The HarmonyOS app defaults to public XEngine spatial upscale in `"native_quality"` mode. Before normal game startup, `GameDefaults.ets` applies the verified MatePad Pro Max quality/performance settings once, excluding its device-specific resolution. It backs up the previous configuration, preserves unknown fields and saves `playable_defaults_version:1`; subsequent player changes are retained. The app sets `spatial_upscale_match_display:true` so input/output dimensions fit the startup XComponent aspect ratio within the selected mode's maximum dimensions. At 3184×2232 this gives 1142×800 rendering and 1712×1200 output, rather than stretching the old fixed aspect. Both dimensions remain even and neither pixel budget exceeds the original mode bounds. A cold process restart picks up a changed window aspect; existing in-flight GPU contexts retain their startup dimensions.

At the low-level runtime, `spatial_upscale_mode:"native_quality"` has maximum input/output bounds 1202×800 / 1802×1200; `"performance"` uses 802×534 / 1202×800. Omitting or disabling `spatial_upscale_match_display` retains the original exact dimensions, including independent GPU fixtures. `"off"`, a missing mode or an invalid mode keeps the ordinary path, while the app's first-run migration supplies the default mode. An active SR mode takes precedence over `resolution` and `MUGUET_RES`; switching OFF restores normal resolution/scale precedence. `spatial_upscale_sharpness` accepts a finite number in [0,1], default 0.2. A cold process restart is required for mode changes.

The runtime reports game-render and active output dimensions separately in `spatialUpscale` status and startup/fallback logs. Native recorded frames are CPU encoding observations, not GPU correctness certification; no generated/display-frame claim is made. Only RGBA8_UNORM (direct) or BGRA8_UNORM (an explicit WGPU textureLoad render pass into a separate RGBA8_UNORM input), 2D with one mip/layer/sample exactly matching the mode input, is accepted. Each completed frame slot retains its own converted input texture/view and source bind group; the conversion preserves logical RGBA channels and alpha instead of aliasing BGRA storage as RGBA. Unsupported capabilities, format/extent, CPU encoding rejection, or unconfirmed frame-slot completion fall back to the original 1:1 blit and original game-sized surface, with a reason. No silent BGRA/sRGB/float reinterpretation is performed.

wgpu30 forbids mixing WGPU and raw recording on one encoder. SR instead uses `[tracked game + optional BGRA-to-RGBA conversion + output Clear/Store + native input RESOURCE, Raw-only XEngine, ordinary WGPU blit]` command buffers in the existing single queue submission. The bridge supplies real output pre/post barriers; native contexts, input/output views and textures are retained in three frame slots until the existing UBO submission fence completes. No extra per-frame submit, queue or wait is added; context teardown waits once at shutdown. SR OFF does not create contexts or extra command buffers.

When SR is requested, the public `VK_LAYER_UNIQUE_HANDLES=0` setting is applied before Vulkan instance creation to prevent passing wrapped non-dispatchable handles into the vendor SDK; core/shader/layout validation remains enabled. OFF restores the previous environment value. A nonempty legacy `VK_LAYER_DISABLES` is rejected because it can override this setting. Custom validation-layer settings must not override wrapping policy; independent negative-control and image/guard validation are required before claiming a supported VVL/SR combination. This setting changes handle wrapping, not rendering quality or validation rules.
